## 1. Layering

```
┌──────────────────────────────────────────────────────────────────────────┐
│ Presentation (BugReport.Runtime: Presentation/, UI/, DebugTools/)        │  reads state, never decides
├──────────────────────────────────────────────────────────────────────────┤
│ Unity adapters (BugReport.Runtime)                                       │  MonoBehaviours: physics, scenes,
│   GameEntity, TargetScanner, AnomalyMotor, PlaceholderHero, …            │  components ↔ ids
├──────────────────────────────────────────────────────────────────────────┤
│ Input (BugReport.Runtime: InputHandling/InputReader)                     │  only place that touches devices
├──────────────────────────────────────────────────────────────────────────┤
│ Core rules (BugReport.Core, noEngineReferences = true)                   │  pure C#, unit-tested outside Unity
│   EntityRegistry, SelectionModel, TargetValidator, GameStateMachine,     │
│   ProgressMonitor; later: GlitchManager, ModifierStack, Containment      │
└──────────────────────────────────────────────────────────────────────────┘
```

Rules:
- **Core never references UnityEngine.** This is enforced by the asmdef (`noEngineReferences: true`) and by compiling Core as `netstandard2.1` / C# 9 in `Tools/CoreTests`.
- Core holds **ids, not object references.** Every Unity object can be destroyed at any time. Core resolves ids through `EntityRegistry`, which prunes dead entries.
- Input is read in one place (`InputReader`). Gameplay components take plain values (`AnomalyMotor.Tick(planar, vertical, boost, basis, dt)`), so tests, cutscenes, and AI can drive them without devices.
- Presentation subscribes to state and draws. It never mutates gameplay state.

## 2. Services and lifecycle

`GameServices` is a plain C# per-level composition root. It holds `Registry`, `Selection`, and `State`.

- `GameBootstrap` has `[DefaultExecutionOrder(-1000)]`. It creates and installs the services in `Awake` and disposes them in `OnDestroy`. Disposal clears every registration and selection, so **nothing survives a level restart**.
- Components that may initialise before the bootstrap use `GameServices.WhenReady(callback)` and cancel it in `OnDisable`. This removes any dependency on scene load order.
- Statics are reset with `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]`, so Enter Play Mode Options with Domain Reload disabled stays safe.
- If a stale `GameServices` is found whose owner bootstrap is already destroyed (an edge case in teardown order on reload), the new bootstrap disposes it and continues. A genuine second bootstrap logs an error and disables itself.
- *(planned, M5/M8)*: a persistent `Bootstrap.unity` scene owns cross-level services (settings, save, audio, scene loading). Per-level services stay as they are.

`GameStateMachine` defines the states Boot, MainMenu, Playing, Inspection, Paused, LevelTransition, and Ending. Transitions are explicit in a table. Pause remembers whether to resume into Playing or Inspection. A test checks that every state can reach Playing, so the flow graph has no dead ends. `GameStatePresenter` applies the state to the engine (cursor lock, `Time.timeScale = 0` while paused) and restores the defaults when destroyed.

## 3. Entities and capabilities

`GameEntity` (MonoBehaviour) implements `IEntityDescriptor`, which exposes Id, DisplayName, Category, Capabilities, and IsAlive.

- **GameEntityId** is a runtime int assigned by the registry. It is monotonically increasing and **never reused** within a registry lifetime, so a stale id can never resolve to a different object. It is not used for saves. Saves will use authored stable ids *(planned, M8)*.
- **EntityCategory** values are Prop, Structure, Decoration, Hero, Enemy, Objective, SystemDevice, and Anomaly. Requirements can exclude categories, and the anomaly is always excluded.
- **EntityCapabilities** is a `[Flags]` enum: Inspectable, CollisionTransferable, Duplicable, Freezable, PropertyMutable, AIControllable, and ObjectiveRelevant.
  - In M1 the flags are **declarative data** used for selection validation and debug display.
  - From M2, every glitch requires **both** the flag and a matching capability component (`CollisionCapability`, `FreezeCapability`, `DuplicationCapability`, …). The component is the only code allowed to change that aspect of the object. This is the "explicit capabilities, no unrestricted component manipulation" rule. A flag without its component fails validation with a clear reason, so declarations can never silently do nothing.
- `TargetRequirement` (required capabilities + excluded categories) feeds `TargetValidator`. It returns a typed failure (NoTarget, Destroyed, CategoryNotAllowed, MissingCapability) and a player-facing reason. Glitch definitions will generate their requirement from designer data.

## 4. Targeting and selection (implemented)

```
Camera ─▶ TargetScanner ──(GameEntity)──▶ SelectionController ──(GameEntityId)──▶ SelectionModel (Core)
         sphere cast, nearest hit,            feedback events                  hover/selected ids,
         ignores anomaly hierarchy            (UI/audio)                       validation, auto-clear
```

- The scanner casts a thin sphere from the screen centre, takes the **nearest** hit (walls occlude), skips the anomaly's own hierarchy whatever its layer, and resolves `GetComponentInParent<GameEntity>()`. It is allocation-free.
- The targeting mask deliberately **includes the `Intangible` layer**. Collision Transfer moves objects there, and they must stay selectable so the player can inspect or restore them.
- `SelectionModel` listens to `EntityRegistry.Unregistered`. A destroyed or disabled entity cannot stay hovered or selected.

## 5. Glitch system *(framework + Collision Transfer: M2; Duplication + Freeze: M3)*

### 5.1 Data and runtime objects

| Type | Kind | Responsibility |
|---|---|---|
| `GlitchDefinition` | ScriptableObject | Designer data: id, name, description, icon, colour, cost/cooldown, duration (0 = until reverted), `TargetRequirement` (capabilities + allowed categories), arity (1 or 2 targets), containment weight, VFX/SFX references, revert-on-patch flag. |
| `IGlitchEffect` | C# interface (Core) | Strategy implementing one glitch: `Validate(targets)`, `Apply(ctx) → op`, `Revert(op, reason)`. Pure where possible; touches Unity only through capability interfaces. |
| `GlitchOperation` | Core class | One applied modification: OperationId, definition id, target EntityIds, start time, expiry, `OperationState`, owned modifier handles, debug label. |
| `GlitchManager` | Core class | Owns active operations, applies the conflict policy, ticks expiry with injected time, reverts (single, LIFO "R", by target, all), and cascades invalidation. It emits events for containment and presentation. |
| `GlitchController` | MonoBehaviour | Player workflow only: chosen glitch → target collection → request to the manager → feedback. It holds no per-glitch logic. |

### 5.2 Operation lifecycle

```
            Validate ok        expiry / R / cancel / patch
Requested ─────────────▶ Active ────────────────────────────▶ Reverting ─▶ Ended(reason)
    │                       │  target destroyed / scene unload
    └─▶ Rejected(reason)    └──────────────────────────────▶ Invalidated ─▶ Ended(reason)
```

- **Reverted** restores owned modifiers. **Invalidated** means the target is gone: the operation drops its handles and does no restore work on dead objects. Neither path can throw on a destroyed target, because every access goes through `registry.TryGet`.
- Scene unload calls `GlitchManager.EndAll(SceneUnload)` before `Registry.Clear()`.
- Pause stops expiry because the manager ticks on scaled time.

### 5.3 Reversibility: modifier stacks, not snapshots

This is the central safety decision. **We never restore a stored snapshot of a Rigidbody, GameObject, or component.** Snapshots break when another system (gameplay, another glitch, a containment patch) changes the same object in the meantime.

Instead, every mutable aspect is a **channel** owned by its capability component:

```
ModifierStack<T>   (Core, generic, unit-tested)
  Base value          ← written only by authoritative gameplay/authoring
  Modifiers[]         ← (OperationId owner, priority, value)
  Effective value     = highest-priority modifier, or Base if none
  Add(owner, value) → handle;  Remove(handle) → recompute and push Effective to Unity
```

Examples of channels: `PhysicsLayer` (collision), `IsKinematic` and `LocalTimeScale` (freeze), `Mass`, `Bounciness` and `UniformScale` (property swap, later).

Consequences:
- Reverting removes **only that operation's** modifier. If gameplay changed the base meanwhile, the base is what returns.
- Two operations on the same channel never corrupt each other. The **conflict policy** is declared per channel:
  - `Exclusive` (default) rejects the second operation with feedback such as "OBJECT ALREADY FROZEN".
  - `Stack` resolves by priority.
- Operations on different channels of the same object (freeze plus collision) compose naturally.

### 5.4 Collision Transfer *(implemented, M2)*

- **Semantics:** select a SOURCE (E), aim at a TARGET, apply (LMB).
  - The source must currently be **solid**; it becomes intangible.
  - The target must currently be **intangible**; it becomes solid.
  - R reverts the most recent glitch.
- **Implementation:** `CollisionCapability` owns an exclusive `ModifierStack<CollisionMode>` over an **explicit, authored collider list**. Children are never discovered automatically.
  - Solid: each collider sits on its solid layer, captured from authoring, or `solidLayerName` for objects authored intangible.
  - Intangible: each collider sits on the `Intangible` layer, which collides with nothing but stays targetable.
- **"Latent" colliders:** objects authored intangible (shadow decal, holo panel) already carry their collider on the Intangible layer. No colliders are ever created at runtime.
- **Safety, decided and tested:**
  - **Occupancy:** a target cannot turn solid while the hero, the anomaly or a prop is inside it ("TARGET OCCUPIED BY …"). `PhysicsOccupancy` uses oriented boxes for BoxColliders and an AABB fallback otherwise, shrunk by 2 cm so touching doesn't count.
  - **Blocked revert:** a normal revert or expiry **waits** while something is inside the source, since it would turn solid around it ("CANNOT RESTORE …"). Expiry retries every frame. Forced endings (target lost, level unload) always proceed.
  - **Dynamic bodies:** a source with a non-kinematic Rigidbody is **rejected** ("MOVING OBJECTS CANNOT LOSE COLLISION"). It would fall through the floor. Revisit when Freeze (M3) can supply a kinematic modifier.
  - **Capability check:** an entity declaring `CollisionTransferable` without a `CollisionCapability` is rejected with a clear message, and an EditMode test fails the scene.
- `Physics.IgnoreLayerCollision` is never called at runtime. The matrix is project configuration only.
- **Data:** `CollisionTransferDefinition` (ScriptableObject) at `Assets/_Project/ScriptableObjects/Glitches/GL_CollisionTransfer.asset`. The builder never overwrites it once it exists.
- **Feedback (placeholder):**
  - `CollisionModeVisual` swaps materials: ghost when intangible, glowing when solidified.
  - Glitched entities keep an electric-blue outline.
  - `GlitchPulsePresenter` fires a 0.6 s beam from source to target.
  - The reticle turns red or cyan from the live apply preview.

### 5.5 Duplication *(implemented, M3)*

- **Who can be copied:** only entities with the `Duplicable` flag **and** a `DuplicationCapability` → `DuplicationProfile` (ScriptableObject) → **prefab asset**.
  - The profile exists because a prefab cannot reference itself: Unity remaps self-references to the new instance on Instantiate, which would silently clone the live scene object.
  - An EditMode test fails the scene if a profile points at a non-asset.
- **Spawning:**
  - The copy is instantiated from the prefab under an **inactive holder**, so nothing on it runs until identity (name, capabilities) and lineage (`DuplicateMarker`: origin, generation, operation) are set.
  - Then it is activated and registers with a new `GameEntityId`.
  - Approved state copied: pose, scale, and optionally velocity (profile). Glitch state is **never** cloned (a copy of a frozen crate is not frozen) and external references are not copied.
- **Placement:** the first free spot beside the source (right, left, front, back, top; `Physics.CheckBox` ignoring Intangible). Otherwise rejected: "NO SPACE".
- **Limits:** `DuplicationDefinition.MaxActive` is the global cap; `DuplicationProfile.MaxCopiesPerSource` is the per-source cap.
- **Lifetime:** the copy is the operation's **product** (`GlitchOperation.AddProduct`).
  - Reverting despawns it, through a lease.
  - Losing the copy for any reason ends the operation (TargetLost), which frees the copy budget.
  - Anything glitching the copy ends with it. Copies of copies collapse in a chain.
- **Objectives:** `NotObjective` (default) strips `ObjectiveRelevant` from copies; `Inherit` keeps it (the "confused objective" gag, M5).
- **Not yet:** a kill plane for copies that fall out of the world (M5).

### 5.6 Freeze *(implemented, M3)*

- **Mechanism:** `FreezeCapability` holds an exclusive `ModifierStack<bool>` and is the only code allowed to change the entity's `Rigidbody.isKinematic` and Animator speeds while frozen.
  - **Frozen:** the body turns kinematic, so forces and gravity are ignored and nothing accumulates. Animator speed goes to 0. Scripted movers (`ITimeScaled`, e.g. `PingPongMover`) read `TimeScale` = 0 and resume from the same phase.
  - **Unfrozen:** the kinematic flag returns to the value it had before freezing. A dynamic body is released **at rest**. The flag is set before velocities are written, which Unity 6 requires.
- **Momentum:** `FreezeDefinition.Release = RestoreMomentum` returns the velocity captured **in the operation** (clamped to `MaxReleaseSpeed`), and only for non-forced endings.
- **Limits:** the definition gives Freeze a duration (8 s default) and max active (3). The hero is excluded until AI Override exists.
- **Interplay:** `CollisionCapability.HasDynamicBody` uses the **authored** body state, so a frozen (temporarily kinematic) crate still can't become an intangible collision source.

### Presentation arbitration

`RendererOverrides` owns material overrides per entity with priorities (freeze 20 > collision 10). Without it, two visuals each restoring the materials they remembered would overwrite each other.

### 5.7 Multiple glitches interacting (rules)

1. Each operation owns modifier handles only. Ownership is tracked, so revert is O(own handles) and never touches others.
2. Destroying a target invalidates every operation on it. Despawning a duplicate cascades.
3. The `R` key reverts the most recent **still-active** operation (LIFO, skipping ended ones).
4. Containment patches revert through the same API with reason `Patch`.
5. Cross-channel combinations need a test before they ship: freeze + collision, duplicate a frozen object (the copy is not frozen), collision on a duplicate followed by despawning the duplicate.

## 6. Hero *(implemented, M4)*

**Navigation decision.** I chose an authored waypoint graph with live physics passability over NavMesh. Recorded in M4.

- A baked NavMesh ignores runtime collision changes. Collision Transfer, Freeze and Duplication change what is solid constantly, so NavMesh would need every glitchable object kept in sync through obstacle carving, plus runtime rebakes for surfaces that become walkable.
- With the graph, `HeroNavGraph.IsPassable` is a capsule sweep against `World|Props` at query time. Intangible objects, the anomaly and the hero itself are excluded, and low steps (pads, decals) are ignored. A glitch changes routes instantly, with zero nav data to maintain.
- The routing itself is the engine-free `NavGraph` (A*, deterministic tie-breaks). When the goal is unreachable it returns a **partial path** to the reachable node closest to the goal.
- **Trade-off:** levels need authored nodes. That is acceptable for a handcrafted puzzle game where the hero "follows the script". Revisit if levels become open.

**`HeroController` states (FSM):**

| State | Behaviour |
|---|---|
| Idle | waits out the start delay |
| Walking | follows the route; re-checks the next edge every 0.4 s; stall detection via `ProgressMonitor` |
| Blocked | no full route: walks as far as possible, then waits at the obstacle and re-plans every 2 s, or within 0.3 s of any glitch starting or ending |
| Confused | the next edge became blocked, or it got physically stuck: pauses 1.2 s, then re-plans |
| Arrived | at the goal |

- It moves with a CharacterController, so it is physically blocked by what is solid.
- It never walks backwards to a node when no progress is possible; it waits at the obstacle.
- It is deterministic and uses no randomness.
- Investigate, Chase and the rest of the AI Override states come with that glitch (deferred, GDD Part 11).

## 7. Containment *(implemented, M4)*

**`ContainmentModel` (core, deterministic, unit-tested).** Pressure (0–100) comes only from explicit sources:

| Source | Effect |
|---|---|
| Glitch applied | impulse = spec `ContainmentWeight` × 10 |
| Glitches active | + weight × 1/s |
| Duplicates existing | + 0.5/s each |
| Anomaly sighted *(input exists; no sensors yet)* | + 8/s |
| Restricted target modified *(input exists)* | + 15 |
| Decay | − 1.5/s, always |

- Because decay always applies, normal play returns to stage 0.
- Stages 1–4 have separate enter thresholds (20/45/70/90) and exit thresholds (12/35/60/80), so stages don't flicker.
- All of these values are tunable in `ContainmentSettingsAsset` (ScriptableObject).

**`ContainmentDirector` (runtime) responses:**
- **Cooldowns:** multiplied by stage (×1.5 from stage 2, ×2 at stage 4), through `GlitchManager.CooldownScale`, which is clamped ≥ 1.
- **Patches, from stage 3:** every 6 s (3 s at stage 4) the **oldest** revertible glitch is reverted with reason `Patched`, through the same `GlitchManager` API the player uses.
  - The first patch waits one full interval after entering the stage (warning time).
  - A patch the effect vetoes (someone inside a wall that would turn solid) moves on to the next glitch. Patches never trap anyone.
  - Each patch relieves 15 pressure.
- **This is how containment creates opportunities as well as threats:** a patch can re-solidify a wall, or undo a duplicate a sensor was fooled by.
- The director never edits objects directly.

**Presentation:** the HUD (`GameHud`, §8c) shows a pressure bar coloured by stage, a stage banner that flashes when the stage rises, and a patch countdown from stage 3. Patched objects flash red/white.

**Deferred:** drones and sensors (anomaly sighting), stage-4 route shutdowns, audio alerts. They need the vertical-slice level and audio set (M5).

## 8. Level, objectives, UI, audio *(implemented M5)*; save and settings *(planned, M8)*

- **Objectives:** `ObjectiveDirector` holds authored entries (id, title, hint, `ObjectiveCondition`) and drives the core `ObjectiveTracker`.
  - Conditions are explicit components (`HeroReachedZone`); scene names are never checked.
  - Objectives describe **what** to achieve, not how, so alternative solutions count without extra work.
  - When all are complete the state goes to `Ending` and the level-complete screen shows.
- **Level machinery:**
  - `PressurePlate` polls an overlap volume. Any rigidbody ≥ min mass counts: frozen bodies and duplicates too, but not characters.
  - `GateController` opens when all plates are pressed and **latches**, so it can never close on the hero. It calls `GameServices.RaiseWorldChanged()` so a waiting hero re-plans.
  - `HeroHazard` marks dangerous machinery with a **static** danger volume:
    - Route segments crossing it are impassable unless the machine is frozen or intangible. This is checked in planning and every frame while walking.
    - Unfreezing or restoring the machine is **vetoed** while anyone is in the volume, so the hero can never be crushed.
- **Fall recovery:** `WorldBoundsGuard` puts originals back at their spawn pose and removes copies that fall below the kill plane, so puzzles can't be softlocked by lost items.
- **UI:** UI Toolkit layers (§8c). Restart (`LevelFlow.RestartLevel`) reloads the scene, which recreates all services.
- **Audio:** `ProceduralSfx` synthesizes original placeholder sounds at runtime, so there is nothing to license. `AudioFeedback` maps game events to sounds: select, invalid, per-glitch tone, undo, patch, stage alerts, objective chimes.
- **Not yet:** save data uses versioned POCOs with authored stable ids, and no Unity references are persisted. Settings live in a separate file. Input rebinding uses `SaveBindingOverridesAsJson` on the runtime action copy. **(M8)**

## 8b. Presentation *(M6 pass 1)*

- **Rule:** presentation reads state, never drives gameplay. Animation moves visual pivots, not physics transforms.
- **Feature switches:** every feature is gated by `VisualSettings` (`VS_Default` asset). A missing asset means everything is on. This is the rollback switch while visuals are unreviewed.
- **Post-processing:**
  - `VP_BugReport` (URP VolumeProfile, components saved as sub-assets) applied by one global Volume.
  - `GlitchCameraFx` modifies a **runtime copy** of the profile: chromatic aberration and lens distortion bursts on glitch application, a red vignette pulse on patches.
  - Timing comes from the core `BurstEnvelope`/`BurstMixer`, so effects are short and never stack past full strength.
  - The player can disable colour-split effects (`ComfortSettings`, persisted, pause menu).
- **Placeholder art is procedural:** tetrahedron mesh asset, grid texture PNG (through LFS), materials. Models and designed UI replace them in later passes.

## 8c. Game UI *(M6 pass 2, UI Toolkit)*

- **One `UIDocument`** (`PS_BugReport` panel settings: 1920×1080 reference, scale with screen size, Unity's default runtime theme via `BugReportTheme.tss`).
- **Layers** are components deriving from `UiLayer`. Each builds its own subtree in code into the document root and sorts itself by draw order, independent of component order:
  1. `InspectionOverlay` (bottom): world-anchored inspection tags and the hero's state icon (`RuntimePanelUtils.CameraTransformWorldToPanel`), plus the selected-object property panel.
  2. `GameHud`: containment bar and banner, reticle, feedback messages, objective panel, glitch dock with cooldowns, contextual prompt.
  3. `GameMenus` (top): pause screen (resume, colour-split toggle, controls reference, restart, quit) and the level-complete screen. The first button takes focus for keyboard and gamepad.
- **Why code, not UXML:** the tree is small and stable. Built in C#, it is type-checked, and tests can query elements by name. Layout and look live entirely in `Assets/_Project/UI/BugReportUI.uss`, so visual changes don't touch code.
- **Rules:** layers only read state. The only writes are explicit menu actions (resume, comfort toggle, restart, quit). HUD elements never take pointer input (`PickingMode.Ignore`); menu screens block clicks underneath.
- **Engine-free parts:** wording and number formatting (`HudFormat`, invariant culture) and the feedback queue (`ToastQueue`: newest first, repeats collapse into "x2", fade at end of life) are in Core with unit tests.
- **Input:** Unity 6 UI Toolkit reads the Input System directly; no EventSystem in the scene.
- **Still IMGUI:** `DiagnosticsOverlay` (developer tool, F1).

## 8d. Guide / tutorial *(M7)*

- **`GuideDirector`** holds authored steps, each with a section (objective index), a short instruction, a condition and optional target/glitch references.
- **Conditions:**
  - *Latching* (an action happened): Move, Apply, Revert, Inspect.
  - *State* (true only while it holds): LookAt (optionally while something is selected), Select, Equip.
  - WaitForObjective is never met; it is shown until the objective completes.
- **Core `GuideTracker`:** shows the step after the furthest satisfied one in the current section. Deselecting walks back; acting early skips ahead; completing the objective finishes the section whatever the guide said. **The guide can never block progress.**
- **Unlocks:** glitches whose section hasn't started are locked in `GlitchController` (skipped by cycling, hidden in the dock). Unlocking happens in the same call that completes the objective, and announces "NEW GLITCH".
- **Presentation:** `GameHud` shows the instruction above the dock (keys highlighted by `GuideText`). `InspectionOverlay` puts a bobbing marker over the step's target. `AudioFeedback` plays a soft chime the first time each step is passed (not again when a state step is lost and regained).

## 8e. Front end, saves and levels *(M9–M10)*

- **Save:** one JSON file (`SaveStore`, `Application.persistentDataPath`) holding completed level ids, settings and Input System binding overrides.
  - Writes are atomic (temporary file, then replace). An unreadable file is kept as `.corrupt` and the game starts fresh.
  - Values are sanitized on load. Tests redirect the store to a temporary file.
- **Levels:**
  - `LevelCatalog` (`LC_Main`) is the play order with stable ids; progress never uses build indices.
  - Builders keep Build Settings as: main menu, levels in catalog order, dev scenes.
  - `LevelCompletionRecorder` saves completion when the last objective is done.
- **Settings:** `SettingsApplier` (per scene) applies volume, sensitivity, invert Y and fullscreen whenever `SaveStore.SettingsChanged` fires. `SettingsPanel` is shared by the main and pause menus.
- **Rebinding:** `BindingOverrides` lists the rebindable keyboard/mouse bindings and stores overrides as Input System JSON in the save. `InputReader` applies them to its runtime copy at start and on change.
- **Level building:** `LevelKit` composes levels from the same components TRAINING LAB uses.
  - Routes can require solid floor (`HeroNavGraph.requireGround`, raycasts along each edge against solid layers), which makes hologram bridges and moving platforms work with the existing passability model.
  - The hero respawns at its start if it falls below the kill plane.

## 11. Conventions

- Unity 6 API names: `Rigidbody.linearVelocity` (not `velocity`) and `Object.FindObjectsByType` (not `FindObjectsOfType`).
- No `Time.deltaTime` in freezable movers (see 5.6).
- Logs are prefixed `[BUG REPORT]`.
- Debug-only shortcuts (F1, F5) read `Keyboard.current` directly and are not remappable. All gameplay input goes through `InputReader`.

## 8f. Full game: new glitches, guards, presentation *(M11)*
- **Property Swap** (`PropertyCapability`, `PropertySwapEffect`, `PropertySwapMath`): an explicit list of swappable properties (mass, speed), each an exclusive `ModifierStack` channel; limits live in Core (`PropertyLimits`).
- **AI Override** (`GuardController`, `AiOverrideEffect`): decisions are Core (`GuardBrain` FSM, `VisionCone`); the component moves, looks and reports. A guard is a `IHeroHazardSource`: the hero waits while it is unsafe (patrolling, not lured, not frozen).
- **Desync** (`DesyncCapability`): all colliders live under `collisionRoot`, moved by an authored offset; refused if the destination or the resync spot is occupied.
- **Security drones**: report sightings to `ContainmentDirector.ReportSighted()`; containment at stage 3+ patches the oldest revertible glitch.
- **Level kit**: `LevelKit` (+ `LevelKit.Advanced.cs`) builds levels from named parts; `FullGameLevels` is levels 10–20; guard/drone wiring that needs the anomaly or containment is deferred to `Finish`.
- **Run tracking**: `LevelCompletionRecorder` counts playing time (not paused), glitch uses and the worst containment stage, then calls `SaveStore.SubmitRun` (stars/records). `GameMenus` shows them on the level-complete card with the catalog's outro text.
- **Story**: `LevelCatalog.Entry` carries chapter index, par and intro/outro; `StoryOverlay` types the intro on first play; the chapter index also selects the music theme and the scenery/sky theme (`ChapterTheme`).
- **Hints**: `HintDirector` wraps Core `StuckHints`: hint text at tier 2, a world marker on the objective's `focus` entity at tier 3.
- **Music**: `MusicDirector` plays Core `MusicEngine` (original, procedural) via `OnAudioFilterRead` on an AudioSource looping a silent clip; the audio thread touches only the pure-C# engine.
- **Presentation**: `PowerSpectacle` (orb, rays, confetti; line renderers only), `GlitchCameraFx` FOV punch, hero speech bubble in `InspectionOverlay` from Core `HeroBarks`. Shaders: `BugReport/Hologram` and `BugReport/GradientSky` (URP HLSL; `ShaderHealthTests` guards them).
